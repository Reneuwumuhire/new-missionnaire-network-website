# Missionnaire product improvement roadmap

Make one service easy to discover, operate, and revisit. The public watch link should carry a listener from the schedule to live audio to the published replay. Admin should show what needs attention across that journey. Studio should show what each destination has actually confirmed and let the operator recover from a partial failure.

This roadmap builds on the [existing Studio broadcast procedure](../studio/BROADCAST-WORKFLOW-PLAN.md) and [library search](library-search.md). The ordering is a proposal based on the public walkthrough and source review. Baseline metrics and the service pilot will inform follow-up priorities.

## Delivery sequence

| Milestone                      | Website                                                                            | Admin                                                                                      | Studio                                                                                 | Release check                                                                                      |
| ------------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 1. Improve the live experience | Show the right home and Live page action for the current broadcast state           | Link the upcoming service and urgent alerts to the relevant action                         | Verify start and end per destination and make failed steps retryable                   | Public schedule checks pass. A private rehearsal demonstrates recovery from partial start and end. |
| 2. Connect service to replay   | Follow the stable service link to its exact published replay                       | Pilot a service detail and replay handoff view                                             | Rehearse the actual service setup and report recording status for the selected service | Complete one rehearsal of each supported workflow and pilot the handoff on a live service.         |
| 3. Improve library discovery   | Add homepage search, surface listening progress, and share passages at a timestamp | Use pilot feedback to rank the review queue and surface missing language or asset metadata | Improve the most common preflight and recovery steps observed in the pilot             | Complete the listener tasks on mobile and compare the first two milestones with the baseline.      |

The first website and Studio changes can ship independently. The second milestone depends on the recorder and publication paths agreeing on the service identifier before the website relies on it. Each release should have a clear owner for that surface, plus an operator to run the service rehearsal.

## Website

1. **Give the homepage and `/live` a useful primary action in every state.** Show **Listen live** when Missionnaire has public audio flowing, **Next service** with the viewer's local time when a public service is scheduled, and **Listen to the latest replay** when the station is off air and no service is scheduled. Link to the current service's watch page when available and reuse its reminder flow. Provide a library entry point when there is no published replay. Use the existing live state and a small public schedule query. Check that cancellations, reschedules, and private tests resolve correctly after a cache refresh and during an open session.
2. **Carry the public link through publication.** Use `/live/<slug>` for sharing scheduled services. After a service ends, explain that the replay is being prepared when one is expected, and surface it once published. Preserve old `/live?live=…` links and existing private-test access. When a replay is explicitly linked, honor its publication state. Verify that hiding the replay, or publishing another service on the same day, keeps the original link associated with the right service.
3. **Improve finding, resuming, and sharing content.** Add homepage search using `/recherche`, and show **Continue listening** when valid progress exists on the device. Reuse the existing resume store and skip finished or unavailable items. Add **Share from this moment** to the replay share menu. Carry a validated timestamp and audio edition, using that edition's own playback clock. Verify that a recipient can start at the shared position on iOS Safari and Android Chrome, including when the browser requires a tap to play.

## Admin

1. **Make the dashboard action-oriented.** Use the existing attention cards and operational alerts to show the most urgent permitted work first. Start with the next service, an active broadcast issue, and a replay that needs review. Link each item to the relevant service or action. Show the issue, the next action, and its status in plain language. Check the dashboard as a broadcaster and as a content reviewer.
2. **Add a service detail for preparation and handoff.** Put the schedule, watch link, service type, broadcast status, recording, audio edition, captions, transcript, and publication controls in one view. Reuse the current schedule, recorder, and indexing tools. Show what is ready, what is processing, and what requires a decision. Distinguish a service that intentionally has no new recording from one whose recording is missing or failed.
3. **Make the replay association explicit.** Pass the selected service ID to recording creation wherever a new recording belongs to a scheduled service. Let an authorized editor attach an existing replay or backfill a missed recording. Keep legacy matching for older unlinked data. Check duplicate submissions, concurrent edits, and retries so they cannot silently replace a valid association. Keep publication an explicit editor action and record association and publication changes in the existing audit log.

## Studio

1. **Show each destination's public state and recovery action.** Distinguish encoder output, preview signal, and confirmed public state. When one destination succeeds and another fails, keep the successful destination visible and retry only the failed step. Keep the service and recovery action visible for any destination whose end is unconfirmed. Refresh provider state after a timeout, reconnect, or app restart before repeating a start or end operation. Test both directions of partial failure where supported, and verify retries do not interrupt a healthy destination or duplicate publication actions. Update Studio help to match the start, end, and recovery behavior.
2. **Make rehearsal part of service preparation.** Extend the existing private test and preflight flows. For pre-recorded Kinyarwanda, rehearse opening music, the sermon and its subtitles, and closing music. For live Krefeld, check source audio, the interpreter mic and headphones, the caption clock, and the sermon recording marker. Surface the next action and unresolved checks beside the existing controls. Confirm that rehearsal stays private and restart restores a safe state with the interpreter mic closed.
3. **Confirm the handoff at the end of the service.** Show the recording as saving, saved, or needing attention, and link to the relevant Admin service. Distinguish the local safety capture from the cloud recording. For workflows that use an existing sermon, show which replay or asset Admin should use if it is already linked.

## Verification and rollout

- Start with fixtures and private sessions. Verify scheduled, rescheduled, cancelled, on-air, ended, replay pending, and replay published states. Check French and English UI, content language labels, keyboard navigation, and mobile playback on a constrained connection.
- Rehearse destination timeouts, lost connections, Studio restart, recorder failure, and an unavailable replay. Confirm the same service remains identifiable across Studio and Admin. Exercise both normal publishing and manual recovery, and verify that private tests stay out of public listings and notifications.
- Ship API and data changes additively. Verify an older Studio release can still operate against the updated service endpoints during rollout. Pilot the handoff with a broadcaster and a reviewer, capture where they need help, and use those observations to refine milestone 3.

| Measure                              | How to track it                                                                                                                                                                                                                      |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Listener time to successful playback | Time from home or Live arrival to playback that continues for 10 seconds. Reuse the existing playback signal and add the originating surface where needed. Track the share of visits that reach playback alongside the time measure. |
| Services requiring manual recovery   | Share of operated services that need a manual retry or an external console to recover. Track partial starts and ends by destination.                                                                                                 |
| Time to published replay             | Time from confirmed service end to a publicly reachable replay. For services expected to have a replay, report elapsed time and how many are still waiting.                                                                          |

Capture a baseline before rollout and compare it with the pilot. Use the existing analytics and audit paths where practical. Set targets once the baseline and operating constraints are known.
